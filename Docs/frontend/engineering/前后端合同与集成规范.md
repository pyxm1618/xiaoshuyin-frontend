# 前后端合同与集成规范

Engineering Foundation 已冻结，FE-B4 已通过；正式前端开发尚未授权。后端主仓库拥有产品、总体技术、领域、API 和批准后的体验设计。前端拥有工程规范、实现 Spec、测试和交付治理。两仓各自维护 main、CI、PR 和审计，在正式 Integration PR 中回归主仓库。

## 源文件、合同与同步

合同链为 Backend Zod → Fastify Runtime Validation → OpenAPI → Generated TypeScript Types → Frontend Typed Client。类型只消费 `packages/generated/openapi.d.ts`，HTTP 和状态约束来自同提交的 `openapi.json` 与冻结上游文档。禁止手写重复 DTO/schema。导入版本标记保留原文。当前标记 `0.1.0-plan`，不能据此将所有路径标识为可联调、已部署或已获得生产批准。

Authority 和合同各有 source manifest，绑定 GitHub repo、完整 commit、source path/blob、目标路径、SHA-256 和分类；合同额外绑定 OpenAPI 与 info.version。完整性检查重算 Git blob 和内容 hash。初次导入与同步以 GitHub 读取证实 commit→blob。日常开发使用本地快照。后端无关 main 变更不触发同步。

```sh
bun run contract:preview contract <backend-commit> <new-outside-directory>
bun run contract:preview authority <backend-commit> <new-outside-directory>
bun run contract:check --remote
bun run authority:check --remote
```

Preview 只写新目录，输出字节快照、来源与差异。删除 operation 标为 breaking，其余字节变化统一 review-required。审查完整变更，包括 request/response/schema、枚举、required、错误、授权、媒体类型、流、版本及服务端可用性。对 breaking 变更列清受影响客户端、并行版本或迁移顺序，确认依赖与退回方案后进入单独的同步 PR，更新 manifest、sync impact 和受影响 Spec；同一 PR 不混入客户端业务实现。全量审计按最终 head 执行。正式 Step 4 文件新增时需先经同步治理准入范围。

当前流式接入缺口为 V1 技术设计 §18.4 的 `GET /api/v1/ai-runs/{id}/stream` 和 `GET /api/v1/ai-runs/{id}` 未出现在本次锁定的生成合同。对应 Slice 依赖真实合同同步以及真机和网关证据。

具体能力经过 `contract-listed → verified-in-test → approved-for-target` 逐级提供证据。缺路径、类型、服务端部署、权限、审批或平台兼容时记录 Contract Gap，携带 route、现象、目标环境和源提交，停止依赖的业务开发或验收。历史附件在 V1 PRD 已有当前 canonical 内容和合约子规格，引用的原始 Word 与历史镜像保留在后端作追溯。

## 联调边界

Local Backend 由独立服务进程和隔离存储提供；Development / Test Backend 标记部署 SHA、合同版本、来源、非生产地址和权限。使用专用测试账号、最小权限和合成家庭数据，按受众、授权、安全、幂等及恢复验收。Mock / fixture 仅限显式标示的开发模式和测试，生产构建不得载入。真实 API 不可用时登记阻断。生产地址、凭证、家庭内容和监控数据不得流入测试环境。

## 回归主仓库

目标拓扑为 `apps/server/`、`apps/miniprogram/`、`apps/operations/`、`packages/`、`Docs/`、`specs/`、`tests/`。Integration PR 锁定两个仓库的 SHA，保留前端 PR、提交与 spec/evidence 对照，逐路径导入前端实现、规范和测试，检查编号、共享配置、workspace、lockfile、CI 检查、规则和治理注册表。复用主仓库同版本生成合同，解除前端同步副本。联合验收包含干净构建、依赖、合同、权限、Spec 治理及 Scope 适用的集成、真机、视觉；准备 Git 回退点。Bootstrap 只建立独立交付能力，真实合并由未来 Integration PR 执行。

## Authority 变更准入

工程文档使用 `FE-ENGINEERING`、`FE-DELIVERY` 和 `FE-INTEGRATION`，在 Authority Unit Registry 标记为 frontend。Owner 明示的真实批准依据、工程 Authority 文本、下游影响评估、直接相关冻结规划修订及续期 Audit 1 可在同一受控 PR 内收敛；`.specify/engineering-authority-approval.json` 包含 `repository`、真实批准记录 `decision`、`files`（每条路径的 `before` 与 `after` 精确 SHA-256），覆盖实际变更的工程 Authority。直接相关的 `tsconfig.json` 修订可按现行门禁共同交付。无文档变更的批准记录仍独占 PR；保留真实 Owner 批准、冻结规划、独立 Audit 2 和 exact-head CI，候选未批准不得用于实现准入。保持后端来源 manifest 专用于导入内容。

未来正式冻结的 Step 4 文档以上游实际 `Docs/frontend/design-system/<name>.md` 或 `Docs/frontend/screens/<name>.md` 组织为准；已导入的 Step 3 screens 文件保持其既有身份，不因目录名重分类。先通过仅变更 Authority Unit Registry 的独立 PR 按单文件登记 imported unit 和正式冻结记录 `decision`，再从真实批准的后端 commit 做常规同步。CI 核对上游树、原文与 Git blob，并保护已导入条目。前端引入前须确认公开范围和上游冻结证据。

## Freshness 与准入

`authority:check --remote` 与 `contract:check --remote` 分别保留 pinned source commit→blob 的 Integrity 核验，并读取真实 upstream main，对相关受控文件逐一比较 blob。完整性错误与相关版本漂移分开报告；main 只有无关后端变更、相关 blob 相同则不要求同步。相关漂移必须显式影响评估及独立同步 PR，不自动修改 Authority、不静默同步或用旧合同准入。

远端 governance 对同步和真实 planning / implementation 准入检查 freshness。纯治理修复可在受控治理范围内修复门禁，不因此获得业务开发/验收授权；其尚未同步的相关差异必须明列为阻断依赖。门禁输出和独立 Audit 2 均须保留这个边界。
