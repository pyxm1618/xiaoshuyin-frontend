# V1 前端开发与验收规范

Engineering Foundation 已冻结，FE-B4 已通过；正式前端开发尚未授权。适用于工程、合同接入和业务实现 Slice。

## 编号与交付

业务标识用 `FE-001`、`FE-002`，目录依官方 Spec Kit sequential 规则使用 `specs/001-fe-<slug>/`。使用 `--short-name fe-<slug>`，冲突时以脚本实际输出的编号为准；只在当前受控 checkout 创建。未来按现有目录名迁入主仓库前端命名空间或经 Integration PR 映射，保持 FE 标识并验证工具路径。Bootstrap 已使用 FE-B0–B3 完成工程与治理建设，并经 FE-B4 独立审计通过后关闭。

| 阶段 | 人员与产物 |
| --- | --- |
| Specify → Clarify → Frozen Spec | Plan AI 1 读取 Authority 并冻结 Spec。正式实现由 Developer AI 执行。 |
| Plan → Checklist → Tasks → Analyze | Plan AI 2 依据冻结 Spec 制定实现合同，列明验证证据与本轮适用验收。 |
| Audit 1 | Plan AI 2 做 pre-implementation 审计，检查 exact spec / plan / checklist / tasks、依赖、路径和风险，解决 finding 后准入开发。 |
| Implement → Test → Converge | Developer AI 按已准入任务实现和验证，对照上游与真实合同收敛，在 PR 上公开当前候选证据。 |
| Audit 2 | 独立 AI 对准确 PR head 只读、对抗性地读取完整 diff、相邻实现、真实测试和适用证据，记录 PASS 或阻断及 SHA；随着 head 变化失效。 |
| Merge main | Owner 在 CI、独立 Audit 2、讨论解决和其他适用批准证据齐全后执行。 |

审核从具体 finding 出发并限于当前 Scope。未读完整 Exact Head、上游冲突、真实能力不足、测试无法执行或独立角色缺失时 STOP 并记录。修复后复查受影响范围和当前 head。Developer AI 不得完成自己的审计二，CI 通过也不代替审计。禁止缩减标准、伪造证据、借机扩大 Slice 或无止境重复审核。

## Slice 合同

Spec 列 Scope、Non-goals、上游文件及段落/ID、依赖和真实能力、可观察的 acceptance。Plan 限定 Allowed Paths、Forbidden Paths、Verification Commands、STOP Conditions、环境和测试数据，标明视觉及真机适用性。任务用稳定 ID 标注 `[REQ:...]` 和 `[VERIFY:tests/...test.mjs]`，完成项带当前变更绑定、任务摘要、测试文件和实测证据。详见 [规格入口](../../../specs/README.md)。

实现前在单独受审的治理变更登记有限实现路径的 Ownership。共享路径记录联合所有者或使用显式依赖顺序。并行 Slice 独立 checkout、基线和 PR，触碰共享路径前协调，基线变化后重跑受影响检查。实现 PR 改动必须收敛在已登记且 Plan 允许的路径，禁止修改上游 Authority、治理或其他 Slice 来授权自身。

## 适用验收

1. Engineering Correctness 覆盖静态检查、可复现依赖、工程边界、故障处理、治理和必要测试。
2. Business / Contract Correctness 覆盖实际 API、类型、错误、受众、状态真相、版本、并行主线和失败路径。
3. Experience Correctness 对照冻结设计的正确性与体验门禁，覆盖关键状态、真实中断与恢复。
4. Visual Fidelity 在 Step 4 冻结后，核对指定设计版本、关键状态与尺寸并留对照证据。
5. Real-device Acceptance 记录设备/系统/微信/基础库/DevTools、构建、后端环境、操作、实际结果以及相关缺陷。

仅执行 Scope 适用的条目，未启用的能力显式标记。PR 记录 Exact Head、CI run、独立审计条目、依赖变更和未验证项。对真实条件未具备的条目保持 BLOCKED 或 DEFERRED。

## 准入工件与工程路径

实现前在规划 PR 合入冻结的 Spec、Plan、Checklist、Tasks、Analyze 及由 Plan AI 2 形成的 Audit 1 证据。证据绑定五份工件摘要。开发提交重用已合入基线的证据，只能在保持任务定义字节一致时更新完成标记。共享工程配置可在正常规划 PR 登记需要的路径，由同一实现 PR 交付，治理规则和 CI 的变更走治理 PR。详细格式和路径入口见 [规格入口](../../../specs/README.md)。

## Slice 语义声明与实现准入

Spec 明确 `**Kind**: BUSINESS|ENGINEERING` 与 `**Business Semantics**: NONE|CHANGED`，并在 `## Business Semantics Assessment` 写明真实行为、影响范围和依据。BUSINESS 使用 CHANGED；ENGINEERING 若新增或改变用户可观察业务语义也使用 CHANGED，并承担相同上位业务追溯。NONE 只适用于纯工程建设，不允许以改名、文件路径或测试名掩盖业务变化。

涉及业务语义的 Slice 至少引用一个 `[AUTH:V1-PRODUCT]` canonical 产品需求 ID，并以 `[AUTH:V1-TECHNICAL] Phase N：<原文标题>` 引用 §38 适用 Phase 1–6；在 `## Backend and Contract Dependencies` 列出后端依赖及当前 Source Commit、blob/hash、可验证程度和阻断条件。已存在能力逐行写 `[CONTRACT] METHOD /api/v1/...`；缺口写 `[CONTRACT] GAP: <缺失职责与阻断原因>`，不得伪造 operation。多Phase或多后端依赖合法，FE编号独立，不强制前后端Slice一一对应。

纯工程 NONE 使用 `**Phase**: NOT APPLICABLE`，并在语义评估说明其工程 Authority 与 Phase 不适用的依据。声明不替代审查：Audit 1 增加 `semanticAssessment`，包含与Spec一致的 `businessSemantics`、非空 `rationale` 与可追溯 `evidence`，由 Plan AI 2 对 scope、实际语义及依赖作真实判断。静态门禁验证声明、引用、当前合同与版本绑定，不能完整判断业务语义；独立 Audit 2 对当前候选实现及该判断进行对抗性核查。现有Ownership、Frozen Plan、Audit 1与Task Evidence均继续适用。

## 体验验收证据与独立判断

Correctness Gate 与 Experience Quality Gate 各自 PASS 才可 Overall PASS，任一门禁及适用核心时刻保留独立否决权。体验验收继承冻结的五维度 Clarity、Continuity、Emotional Response、Distinctiveness、Reality Orientation、七个 Core Moment、Signature Experience、Reality First、长期连续性与非惩罚性原则，不用平均分或 CI 代替。Growth World 保持 “not everywhere, but not nowhere meaningful”：在适用核心体验中对时间感、连续感、阶段闭合或情绪连续性有实际贡献；删除测试评价体验损失，不能用业务信息、授权或导航受损证明价值。Motion / Sound / Haptics 留给 Step 4 合理设计，不逐项强制也不提前排除。

适用 manual / visual / device 验收的 `tests/evidence/*.json` 必须包含：`type`、`result`、`reference`、准确 `base`、`candidateFiles`（本次 Change Binding 中剔除全部 `tests/evidence/` 后的路径→SHA-256）、`design`（每项 `unit`、实际 `selector`、完整设计文件 `sha256`）、`observedAt`、实际 `environment`、`operations`（每步 `action / expected / actual`）、`artifacts`（实际文件 `path / sha256`）、`defects`、`unverified`。visual / device 至少一份本次候选的真实截图、录屏或适用设备证据；manual 可以无媒体，但环境、真实操作和结果仍须齐全。媒体/文本证据在 `tests/evidence/`，随当前 diff 和 binding 精确核验。证据只含合成或隔离测试内容，避免真实家庭数据和凭证。

任务完成只接受已实际验证的 PASS，不能存在阻断缺陷或未验证事项；条件不足保持 BLOCKED / DEFERRED，不勾选完成。不得空泛 PASS、伪造媒体、用历史结果冒充当前候选，或要求提交内文件自引用包含自身的最终 commit SHA。`candidateFiles` 绑定待验收内容，最终独立 Audit 2 在 PR 之外绑定真实 Exact Head，读取当前候选、冻结设计、实际截图/录屏/设备过程、结果、缺陷和未验证项，判断证据真实性及体验是否成立。机器只核对结构、摘要和覆盖，Developer AI 的 PASS JSON 与 CI PASS 均不是独立体验结论。Head 变化后重新复核受影响证据并由独立审计记录适用性。

本轮没有正式应用代码、冻结 Step 4 实现或实际设备旅程，只修复机制与治理回归，不制造视觉、体验或真机 PASS。

## 上游新鲜度准入

Integrity 继续验证 pinned来源，`--remote`同时读取真实upstream main并逐文件比较受控Authority/Contract的blob；相关漂移经影响评估与独立同步PR处理，无关main变更不阻断。远端治理在同步、真实规划与实现准入检查freshness；纯治理修复的受控例外不授权业务开发或验收。详见集成规范“Freshness 与准入”。
